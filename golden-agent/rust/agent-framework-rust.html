golden-agent for Rust

A small Rust library for building agents from the core elements: model, instructions, tools, loop and state, plus a guard layer and sub agents. Standard library only, no dependencies. Define a few pieces, build an Agent, call run. It mirrors the Java library in design and behaviour.

Rust 1.85 or newer, edition 2024 Zero dependencies 35 tests pass, clippy clean No unsafe code

OverviewWhat it is and why

Agent frameworks bundle the same handful of ideas. This crate keeps those ideas visible and small, so you can read all of it, change any part, and use it as the base for new agents without adopting a large framework.

5core elements, each a small trait or type
3gate outcomes: allow, deny, ask a human
0dependencies, the standard library only
25ported checks, plus 10 adapter and concurrency tests
The design rule behind it: the LLM proposes and never executes. Your code validates, gates and runs every action.

StructureArchitecture and modules

One public entry point (Agent) sits on top of the loop, and the loop depends only on small traits. Dependencies point downwards, so every piece can be replaced.

Get goingQuick start

use golden_agent::prelude::*;

let agent = Agent::builder("support")
    .model(model_client)                                              // 1. model
    .instructions(
        Instructions::for_role("You are a support agent.")            // 2. instructions
            .with_rule("Verify the customer before changing an account."),
    )
    .tool(get_customer_tool())                                        // 3. tools
    .tool(refund_tool())
    .gate(Gates::prerequisites(&[("process_refund", &["get_customer"])]))
    .gate(Gates::require_approval(&["process_refund"], "refunds need approval"))
    .approver(HumanApprover::new(|call, reason| ask_a_person(call, reason)))
    .max_iterations(10)                                               // 4. loop limits
    .build()?;                                                        // validates, returns a Result

let result = agent.run("Refund order O-1 for customer C-1");          // 5. fresh state per run
println!("{}: {}", result.status, result.text);

Guarantees, each covered by a test

  • The loop branches only on stop_reason. It never parses text such as "I'm done".
  • The full message history is sent on every call. Each run creates a new, isolated state.
  • Unknown tools, bad arguments and tool failures become error results the model can read. A panic inside a tool is caught at the loop boundary and reported without its message, so internal details are not leaked.
  • A denied call never runs, and an ask-a-human decision with no approver is denied.
  • iterations equals the number of tool rounds plus one.
  • An Agent is Send + Sync and holds no run state, so one instance can be shared and run from many threads at once. A test runs 16 threads against one agent.

Guard layerGates, humans and filters

A Gate is ordinary programmatic code that runs before every tool call, outside the model. It returns one of three decisions:

Decision::Allow
the tool runs
Decision::Deny(reason)
the model receives an error result with the reason
Decision::AskHuman(reason)
the HumanApprover decides. No approver means deny
PiecePurpose
Gates::prerequisites(&[...])Block a tool until other tools have succeeded, for example refund only after the customer is verified
Gates::require_approval(tools, reason)Ask a human before the named tools run
Gates::allow_list(tools)Only the named tools may run
gate.and(other)Combine gates. The first non-Allow decision wins
HumanApproverPlug in a console prompt, ticket, chat message or web form. Default is deny-all
ResultFilterRuns after the tool and before the model sees the result. Trim, normalise or redact

Multi-agentCoordinator and sub agents

An agent can be given to another agent as a tool. The coordinator is just an Agent whose tools are delegation tools. Share a sub agent with an Arc.

let researcher = Arc::new(
    Agent::builder("researcher")
        .description("Finds facts on a topic and returns claims with sources")
        .model(researcher_model)
        .instructions(Instructions::for_role("You are a research agent."))
        .tool(web_search_tool)
        .build()?,
);

let coordinator = Agent::builder("coordinator")
    .model(coordinator_model)
    .instructions(Instructions::for_role("You are a coordinator."))
    .sub_agent(researcher)         // becomes the tool delegate_to_researcher
    .sub_agent(analyst)
    .build()?;
  • Isolation: a sub agent sees only the task and context the coordinator passes. It never sees the coordinator's conversation.
  • Least privilege: each agent has only its own tools. Use ToolRegistry::subset(...) to share part of a toolset.
  • Structured failure: if a sub agent does not finish, the coordinator receives an error result such as SUB_AGENT_FAILURE agent=... status=NOT_FINISHED iterations=... note=... task=... partial=..., never an empty success. It can then retry, route elsewhere or continue with partial results.
  • Reuse: an Agent holds no run state, so one instance can be run many times, even concurrently.

A typed tool

struct RefundRequest { order_id: String, amount_cents: i64 }

fn refund_tool() -> TypedTool<RefundRequest, String> {
    TypedTool::displaying(
        ToolDefinition::new(
            "process_refund",
            "Refund an order. Requires a verified customer. Returns a confirmation.",
            InputSchema::object()
                .string("orderId", "The order id", true)
                .integer("amountCents", "Refund amount in cents", true)
                .build(),
        )
        .expect("valid definition"),
        |input| Ok(RefundRequest {                          // decode the raw arguments
            order_id: string_arg(input, "orderId")?,
            amount_cents: integer_arg(input, "amountCents")?,
        }),
        |r| Ok(format!("refunded {} cents for order {}", r.amount_cents, r.order_id)),  // run
    )
}

let business_hours = Gate::new(|call, _state| {

    } else {
        Decision::Allow
    }

Reuse itUse it as a library

Add it as a dependency of any Rust project. A separate test crate that depended on it only by path built and ran a working agent.

# Cargo.toml of your project
[dependencies]
golden-agent = { path = "../golden-agent/rust" }

# build everything here: format check, clippy, tests, demo, package
.\build.ps1                    # Windows
./build.sh                     # macOS and Linux
cargo run --example demo       # just the demo

Real modelUsing the Anthropic adapter

The Rust standard library has no HTTPS client, so AnthropicModelClient is generic over an HttpTransport that you supply. The trait has one method, and is usually a thin wrapper over the HTTP crate your project already uses.

impl HttpTransport for MyTransport {
    fn post(&self, url: &str, headers: &[(&str, &str)], body: &str, timeout: Duration)
        -> Result<HttpResponse, TransportError> {
        // send an HTTPS POST and return the status code and body text
        todo!()
    }
}

let client = AnthropicModelClient::from_environment("<model id>", MyTransport)?;  // reads ANTHROPIC_API_KEY
Covered by offline tests with a mock transport
Correct URL, x-api-key, anthropic-version and content-type headers, and a request body in the Messages API shape
A 429 followed by a 200 succeeds on the retry, and server errors and network errors are retried with exponential backoff
Retries stop after the configured limit, and a 400 is never retried
An unknown stop_reason is rejected, never treated as a normal finish
A full tool loop runs through the adapter, including the tool_result sent back

Honest notesLimits and what is not included

Not run against the live API, and needs your transport. AnthropicModelClient has offline tests for its request and response mapping, but it has not been run against the real service from this repository. It also needs an HttpTransport that you write, because the standard library has no HTTPS client. Test it with your own key first. You choose the model id.
  • Toolchain: verified on rustc 1.95.0 only. The manifest declares Rust 1.85 or newer, which was not tested.
  • Not included on purpose: streaming, long-term memory, context compaction, parallel tool execution, parallel sub agents, persistence and tracing. Each one fits behind an existing extension point.
  • Sequential execution: tools in one response run one after another.
  • Tool input is a map of JSON values: there is no JSON crate, so arguments arrive as a map of Json. TypedTool decodes them into your own type.
  • Panics in tools: they are caught at the loop boundary and reported as a generic error, but Rust's default panic hook still prints the panic message to standard error.
  • Packaging: cargo package works offline but warns that the manifest has no license or repository. Add them before publishing.
