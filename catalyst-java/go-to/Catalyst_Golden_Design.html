Read this firstNaming key: three words used everywhere on this page

The word "code" is vague because the LLM can also write code. So this page uses three clearer words instead.

Green

PROGRAMMATIC

Deterministic logic that a developer wrote, tested and versioned before runtime. It gives the same output for the same input and cannot be skipped.

Also called: rule-based, code, deterministic.

Examples: validators, gates, hooks, tool functions, retry limits
Indigo

LLM

The language model. It reasons over text and decides what to attempt. It produces text only, so a proposal, never an action.

Also called: model, brain, probabilistic.

Examples: choosing a tool, drafting an answer, planning sub-tasks
Gray

APPLICATION

The overall program that hosts both. It runs the loop, executes tools, holds the state and contains every programmatic part.

Also called: host app, harness, runtime.

Examples: the agent loop, the workflow engine, the tool runner
PROGRAMMATIC is guaranteed but rigid.
LLM is flexible but only probabilistic.
Workers (amber) are the sub agents. Each one can be LLM-backed or programmatic.

The LLM never executes anything. Rules it must obey live in programmatic logic, not in the prompt. Everything below is this principle applied at larger scale.

Big pictureThe complete layered architecture

The main stack runs top to bottom, one layer per row (L0 to L6), and the labelled connectors C1 to C6 between layers define exactly what travels down, what comes back up and which contract applies. The right-hand rail lists the concerns that cut across every layer. A coverage checklist at the end of this section shows where each concern lives, so nothing is left out.

What flows back up the stack

Cross-cutting concerns

PromptsSteer the LLM only. System prompt, examples, expected output format. Advisory, never enforcement.
Security
  • secrets never in the prompt
  • tool output treated as data, not instructions
  • least-privilege tools per agent
  • identity from the session, not from text
State and memory
  • messages[] history (the API is stateless)
  • workflow state
  • prior findings passed on
Limits and resilience
  • iteration cap, token and cost budget
  • timeouts
  • bounded retries with backoff
Provenance and trustEvery claim keeps its source, page and confidence. Conflicts are annotated, not merged silently.
ObservabilityLogs, traces per iteration, token usage, audit trail of every gate decision.
Testing and evaluationMock client for deterministic unit tests, contract tests for the model client, a few live evals.

Inside any LLM-driven agentThe agent loop

Every LLM-driven component, the coordinator or a subagent, runs this same loop. stop_reason is the only reliable signal that controls it.

1. SendFull message history plus the tools list.
→
2. Model respondsText and maybe tool_use blocks, plus a stop_reason.
→
3. GateProgrammatic check of the proposed tool call.
→
4. Run toolThe application executes it.
→
5. AppendAssistant turn, then tool_result in a user message. Loop to step 1.
stop_reasonMeaningAction
tool_useModel wants a tool runGate, execute, append result, loop
end_turnModel is finishedReturn the final response
anything else, such as max_tokensNot finishedFind out why before continuing
Three anti-patterns: parsing text such as "I'm done", using an iteration cap as the primary stop (it is only a guard rail), and treating a leading text block as completion.

VocabularyEvery core term in one place

Roles
Brain

LLM

Proposes actions and reasons over results. Produces text only.

Veto

Gate, guardrail, hook

Deterministic programmatic logic that allows, denies or modifies an action.

Hands

Executor, harness

The application layer that runs the tool and feeds back the result.

Components
Main agent

AI agent

A goal-driven loop with state, a decision-maker, tools and a stop condition.

Hub

Coordinator

Decomposes, delegates, aggregates and checks coverage. Owns all communication.

Spoke

Sub agent

A specialist worker with isolated context, its own prompt and a restricted tool set.

Outermost

Workflow engine

Enforces order, prerequisites and limits above the coordinator.

Hands

Tool and registry

A callable capability with a definition. The registry means only registered tools can run.

Memory

State, messages[]

The history sent on every call. The API itself is stateless.

Handoff

Context object

Everything a subagent may know, passed explicitly in its prompt.

Trust

Provenance

Each claim travels with its source, page and confidence so conflicts can be annotated.

Escalation

Structured handoff

A self-contained summary for a human: goal, actions taken, root cause, recommended action.

How control is exercised
Deterministic

Programmatic (rule-based)

Fixed logic decides. Same input, same output. Cannot be skipped.

Probabilistic

Prompt-based

An instruction to the model. Steers behaviour but never guarantees it.

Logic in charge

LLM-backed

Programmatic logic controls the flow and calls the LLM at fixed points. Anthropic calls this a workflow.

Model in charge

LLM-driven

The model chooses the next step and tool and decides when done. Anthropic calls this an agent.

Task shape
Path

Closed or open path

Closed: you can list the steps in advance. Open: steps depend on what is found.

Result

Closed or open result

Closed: automated checks or tests can verify it. Open: judged by quality, not exact match.

Rule

Simplest first

Use the simplest architecture that meets the requirement, and add agency only when needed.

The simplest-first ladder

Stage 1
Single LLM call
Good prompt, maybe retrieval. Often enough.
Stage 2
LLM-backed workflow
Fixed steps in programmatic logic. Chain, route, parallelise.
Stage 3
Hybrid
The workflow is programmatic, one open step is an agent.
Stage 4
LLM-driven agent
Model plans and loops, with gates around it.
Moving up a stage never removes the programmatic layer. You change who chooses the next step, not who is allowed to act.

ReliabilityHow failures travel through the design

Sub agentRetries transient errors locally (timeouts, rate limits).
→
Unresolved failureReturns structured error context: type, what was tried, partial results, alternatives.
→
CoordinatorRetries with adjusted context, tries another source, or continues with partial results.
→
Workflow engineFailed step is never marked complete, so downstream steps stay blocked. Critical failure produces a handoff.
Anti-patternWhy it is wrong
Returning an empty result as successThe coordinator cannot tell failure from "nothing found"
Stopping everything on one failureThrows away good work from other subagents
A generic "operation failed"No information to choose a recovery
Unbounded retriesAnother runaway loop, cap them

Open gaps in the Java source

  1. Step is marked complete before the work runs. engine.execute() completes the step, then the coordinator is called. If the coordinator throws, the step already counts as done.
  2. Steps are not mapped to subagents. Every step runs the full five sub-topic research.
  3. No data flows between steps. The report is only printed.
  4. No failure handling and no parallel delegation.
  5. No dependency injection. The engine and workflow create their collaborators with new.

Where Catalyst sits on the design

Task shape: the four-step job flow is a closed path. Today every layer below the workflow engine is plain programmatic logic, so the whole system is a scripted pipeline. The recommended next move is Stage 2: keep the workflow engine in charge and make each subagent LLM-backed through LLMClient. An LLM-driven coordinator is only justified if different goals need different sub-topics.
