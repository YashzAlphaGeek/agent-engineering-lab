Catalyst – Technical Questions & Answers

Deeper, code-level questions on the Catalyst prep guide: loop mechanics, the real Anthropic API, tool design, multi-agent orchestration, context passing, workflow gates, Java design and testing. Click a question to reveal the answer — try answering first.

Topic 1Agent loop mechanics

1.1 Walk through AgentLoopV2 line by line. What are the exit conditions? 
while (!state.isCompleted()) {
    if (state.getIterationCount() >= MAX_ITERATIONS) { warn(); break; }   // guard rail
    state.incrementIteration();
    ClaudeResponse r = client.nextResponse();
    state.setStopReason(r.stopReason());

    if (r.stopReason() == StopReason.TOOL_USE) {
        ToolCall call = r.toolCall();
        BaseTool tool = registry.get(call.toolName());       // unknown name -> stop / error result
        String out = tool.execute(call.input());
        state.addHistory(new ToolResult(call.id(), out));
        continue;                                              // ask Claude again
    }
    if (r.stopReason() == StopReason.END_TURN) {
        state.setFinalResponse(r.text());
        state.setCompleted(true);
        break;
    }
}
Exit conditions: (1) END_TURN — the normal, intended exit; (2) MAX_ITERATIONS — safety only; (3) an unknown tool name (the runner stops). An exception from a tool is a fourth, unplanned exit — see 1.5.
1.2 Why is the iteration cap checked at the top of the loop rather than the bottom? Checking before calling the model means you never spend an API call that would be thrown away. With cap = 2 the loop makes exactly 2 calls (both TOOL_USE) and then stops without ever seeing END_TURN — this is what the simulator shows. Checking at the bottom would allow one extra call (cap + 1 total) and makes the off-by-one harder to reason about.
1.3 Why is iterationCount = 3 but history.size() = 2? iterationCount counts model calls (TOOL_USE, TOOL_USE, END_TURN). history records tool executions (job_search, resume_analyzer). The END_TURN call returns a final answer and runs no tool. General formula: iterations = toolCalls + 1 for a successful run (assuming one tool per response).
1.4 Why must the loop send the full history on every call? The Messages API is stateless. Claude remembers nothing between calls; the only memory is the messages[] array you send. If you drop earlier tool results, the model cannot see what it already did and may repeat tool calls or contradict itself. In Catalyst AgentState.history plays that role. To save tokens, shrink what a tool returns (trim fields, paginate) rather than deleting results or replacing history with a lossy summary.
1.5 What happens if tool.execute() throws? How should the loop handle it? Today an uncaught exception would crash the loop. Better: catch it and feed the failure back so the model can recover. 
try {
    out = tool.execute(call.input());
    result = new ToolResult(call.id(), out, false);
} catch (Exception e) {
    result = new ToolResult(call.id(), "Error: " + e.getMessage(), true);   // is_error = true
}
state.addHistory(result);        // model sees the failure and can retry or choose another tool
In the real API this is tool_result with "is_error": true. Distinguish transient errors (retry with backoff) from permanent ones (tell the model, do not retry) and keep the error text actionable.
1.6 Explain the three exam anti-patterns and why each fails.
Anti-patternFailure mode
Parse text like "I'm done"Wording varies by prompt, language and model version. A false negative loops forever; a false positive exits early.
Iteration cap as the primary stopCuts legitimate long tasks and lets bad loops run until the cap. A cap is a backstop, not control flow.
content[0].type == "text" means doneA single response can contain a text block and a tool_use block (Claude "thinks aloud" then calls a tool). Checking only the first block exits before the tool runs.
The reliable signal is stop_reason.
1.7 Can one response contain several tool calls? What does that mean for ClaudeResponse? Yes. The real API can return multiple tool_use blocks in one response (parallel tool use). Catalyst's ClaudeResponse holds a single ToolCall, a simplification. A faithful model would be: 
record ClaudeResponse(StopReason stopReason, List<ToolCall> toolCalls, String text) {}
The loop would execute all calls (possibly in parallel, since they are independent) and send all results back together in one user message.
1.8 Why does MockClaudeClient keep returning END_TURN after step 3? It is a step counter: after the script is exhausted it defaults to END_TURN. This is a deliberate fail-safe so a test that calls it too many times terminates instead of throwing IndexOutOfBounds. The downside: it can hide a bug where the loop asks for more responses than expected, so tests should also assert the call count.

Topic 2The real Claude API

2.1 Show the exact message sequence for one tool round-trip in the real API. 
// 1. you send
{ "model": "...", "max_tokens": 1024,
  "tools": [ { "name": "job_search", "description": "...", "input_schema": {...} } ],
  "messages": [ { "role": "user", "content": "Find Java jobs" } ] }

// 2. Claude replies  (stop_reason = "tool_use")
{ "role": "assistant",
  "content": [
    { "type": "text",     "text": "I'll search for jobs." },
    { "type": "tool_use", "id": "toolu_01A...", "name": "job_search",
      "input": { "keyword": "java" } } ] }

// 3. you append BOTH the assistant turn and a user turn with the result
{ "role": "user",
  "content": [ { "type": "tool_result", "tool_use_id": "toolu_01A...",
                 "content": "12 results" } ] }
Key rules: append the entire assistant message (including the tool_use block) before the result; the result goes in a user message; tool_use_id must match; tool_result blocks must come first in that user message's content.

2.5 How do you swap MockClaudeClient for the real SDK in this design? Implement LLMClient with a class that builds the request from AgentState (history -> messages, registry -> tools), calls messages.create(), and maps the SDK response to ClaudeResponse. 
class AnthropicLLMClient implements LLMClient {
    public ClaudeResponse nextResponse(AgentState s, ToolRegistry reg) {
        var resp = sdk.messages().create(buildParams(s, reg));
        StopReason sr = switch (resp.stopReason()) {
            case "tool_use" -> StopReason.TOOL_USE;
            case "end_turn" -> StopReason.END_TURN;
            default -> throw new IllegalStateException("Unhandled: " + resp.stopReason());
        };
        return toClaudeResponse(resp, sr);
    }
}
Important: the guide's description of nextResponse() takes no arguments (the mock ignores state). A real client needs the state/history and tools, so the interface signature must grow. This is the one place "only the client changes" is a slight simplification.
2.6 What else changes when you go live (cost, reliability)?
  • Non-determinism: same input may yield different tool sequences — tests use the mock; add a few live evals.
  • Latency/cost: every iteration is a paid round-trip; the whole history is re-sent each time (use prompt caching for the stable prefix: system prompt + tools).
  • Errors: 429/5xx/overloaded need retry with exponential backoff; timeouts need a deadline.
  • Secrets: API key from environment/secret store, never in source.
  • Context growth: long loops can exceed the context window — trim tool outputs.

Topic 3Tools, schemas and the registry

3.1 What makes a good ToolDefinition? The model sees only name, description and schema. Good definitions: a specific verb-noun name; a description saying what it does, when to use it, when not to, and what it returns; a tight JSON Schema with typed, described, required parameters and enums where values are finite. 
{ "name": "job_search",
  "description": "Search job postings by keyword and location. Use for finding openings, NOT for analysing a resume. Returns up to 10 postings with title, company, URL.",
  "input_schema": { "type": "object",
    "properties": { "keyword":  {"type":"string","description":"e.g. 'java'"},
                    "location": {"type":"string","description":"City, optional"} },
    "required": ["keyword"] } }
Two tools with overlapping descriptions cause mis-selection — fix the descriptions first, not the prompt.
3.2 Why is Object execute(Object input) a weak signature, and how would you improve it? An untyped Object in and out (the shape used by Catalyst's BaseTool) forces every tool to cast and parse its own input and gives no compile-time safety. The tool's own code, for example String.valueOf(input), decides what the input means. Better: a typed input (record) validated against the schema, and a structured result. 
interface BaseTool<I, O> {
    ToolDefinition definition();
    O execute(I input) throws ToolException;
}
Validate model-produced input before executing: the model can emit missing or wrongly-typed fields. Return validation errors as an is_error result so the model can correct itself.
3.3 How does the registry act as a security boundary? What does it not protect against? Only registered tools can be executed, so a hallucinated tool name fails the lookup instead of running arbitrary code. It does not protect against misuse of a legitimate tool (bad arguments, prompt injection from tool output telling the model to call a destructive tool). Add: least-privilege tools, argument validation, allow-lists, human confirmation for destructive actions, and treat tool output as untrusted data.
3.4 get(name) returns null for an unknown tool — what is the better design? Return Optional<BaseTool> or throw a specific UnknownToolException, and have the loop convert it into an error ToolResult ("Unknown tool 'x'. Available: job_search, resume_analyzer") so the model can self-correct rather than the program stopping silently.
3.5 How many tools should one agent have? Fewer is better. Reliability of tool selection degrades as the list grows and overlaps (a rule of thumb is to keep an agent to a handful of focused tools). If you need many, split by role across subagents (Topic 4), each with a narrow tool set, or load tools dynamically.

Topic 4Multi-agent orchestration

4.1 Why hub-and-spoke instead of agents talking to each other?
  • Observability: one place to log every delegation.
  • Consistent error handling: the coordinator decides retry / skip / escalate.
  • Controlled information flow: subagents only see what the coordinator passes (isolation).
  • Less coupling: N specialists need N links to the hub, not N² to each other.
Cost: the coordinator is a bottleneck and single point of failure, and it may decompose too narrowly.
4.2 Make delegate() run sub-topics in parallel in Java. What must be true? Sub-topics must be independent. Note that in Phase 4 they are not fully independent because priorFindings feeds each into the next — parallelising forces a choice: drop the chaining for independent topics, or run in dependency stages (parallel stage 1: Job Search + Resume Analysis, then stage 2: Skills Match using both). 
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {          // Java 21
    List<Future<ResearchFinding>> fs = topics.stream()
        .map(t -> ex.submit(() -> agentFor(t).research(ContextBuilder.build(goal, t, List.of()))))
        .toList();
    List<ResearchFinding> findings = new ArrayList<>();
    for (var f : fs) findings.add(f.get());          // or CompletableFuture + allOf
}
Also consider: per-subagent timeout, partial failure (one fails, others still return), and thread-safety of any shared state. In the Claude Agent SDK equivalent, you emit several Task tool calls in one response.
4.3 The coverage metric always returns 100%. Diagnose and fix it. Diagnosis: completeness = findings.size() / topics.size(), and the code always creates one finding per sub-topic, so numerator = denominator. gaps is hard-coded empty, and "covered" lists agent names (retrievedBy) instead of topics — the metric cannot fail.
Fix: tie each finding to the sub-topic it answers and require real evidence. 
Set<String> covered = findings.stream()
    .filter(f -> f.metadata() != null && hasEvidence(f))         // source or doc present, claim non-blank
    .map(ResearchFinding::subTopic)                              // needs a subTopic field on the record
    .collect(toSet());
List<String> gaps = planned.stream().filter(t -> !covered.contains(t)).toList();
double completeness = planned.isEmpty() ? 0.0 : (double) covered.size() / planned.size();
Then add the missing refine step: re-delegate each gap (bounded retries). Remember coverage vs. the plan still cannot detect a topic the plan never included.
4.4 delegate() uses a switch with default -> SkillsMatchAgent. What is the risk? Unknown or new sub-topics are silently routed to the wrong specialist and still "succeed", so coverage looks fine while the content is irrelevant (Salary Analysis answered by SkillsMatch). Fix: make the default throw or return "no capable agent" so it shows up as a gap; better, use a Map<String, SubAgent> / common SubAgent interface so adding an agent is registration, not editing a switch (Open/Closed).
4.5 What common interface would you introduce for the three subagents? 
interface SubAgent {
    String topic();                                   // what it handles
    ResearchFinding research(ResearchContext ctx);
}
Map<String, SubAgent> agents = Map.of("Job Search", new JobSearchAgent(), ...);
The coordinator then depends on an abstraction, can be tested with fake subagents, and the same pattern as LLMClient / BaseTool is reused.
4.6 When is multi-agent the wrong choice? When one agent with a few tools can do the job: multi-agent adds latency, cost (each agent has its own context/tokens) and coordination bugs. Use it when tasks are genuinely parallelisable, need different tool sets / permissions, or would overflow a single context window.
4.7 How do you handle a subagent that fails or returns nothing? Return a structured failure (error type, what was attempted, partial results) rather than an empty success. The coordinator then decides: retry, route to another agent, proceed with partial coverage and report the gap in the final output, or escalate. Silently swallowing the failure produces a confident but incomplete report.

Topic 5Context passing & provenance

5.1 Why isn't it enough to just "trust" the subagent knows the situation? A subagent is a fresh model call with its own prompt; it has no access to the coordinator's conversation. Anything not in ResearchContext does not exist for it. So the context object must carry the goal, assigned sub-topic, expected output format and relevant prior findings.
5.2 priorFindings is a String built with "- " + claim. What are the weaknesses?
  • Loses provenance — source, page, confidence are dropped, so the next agent cannot weigh evidence.
  • Unbounded growth — with many agents the string grows and burns tokens; pass only relevant findings.
  • Unstructured — the prompt-injection and parsing surface is larger than a typed list.
Better: List<ResearchFinding> priorFindings, serialised into the prompt with claim + source + confidence, filtered to what the subagent needs.
5.3 Why are some ResearchMetadata fields allowed to be null? Because a source may not exist (SkillsMatch has no URL). A null honestly says "unknown"; inventing a URL would be fabrication and would poison downstream trust. Use Optional or explicit fields in the type, and let the aggregator display "source unknown" rather than hide it.
5.4 Two subagents return conflicting values for the same fact. What should the synthesis do? Do not silently pick one or average. Keep both with their sources and confidence, annotate the conflict (and the dates if they differ — it may be a time difference, not an error), and let the report or a human resolve it. This is exactly why a claim must travel with its ResearchMetadata.
5.5 How would you protect the pipeline from prompt injection in tool/web content? Treat all tool and retrieved content as data, not instructions: delimit it clearly in the prompt, never let it change tool permissions, validate the arguments of every tool call the model proposes, keep destructive tools behind confirmation or code gates, and give subagents minimal tool sets so an injected instruction has little to abuse.

Topic 6Workflow enforcement & handoff

6.1 Explain why "prompts are not enforcement". A prompt shifts probabilities; it does not guarantee behaviour. Under long context, odd inputs or adversarial text, the model may skip a step. A canExecute() check in code runs every time and cannot be argued out of. Use code gates where failure is costly (financial, security, regulatory, ordering that affects correctness); use prompts for style and judgement.
6.2 How would you make the validator more general than the linear switch? Data-driven prerequisites, so non-linear workflows (diamond dependencies) work: 
private static final Map<WorkflowStep, Set<WorkflowStep>> PREREQS = Map.of(
    SEARCH_JOBS,              Set.of(),
    ANALYZE_RESUME,           Set.of(SEARCH_JOBS),
    MATCH_SKILLS,             Set.of(SEARCH_JOBS, ANALYZE_RESUME),
    GENERATE_RECOMMENDATION,  Set.of(MATCH_SKILLS));

boolean canExecute(WorkflowStep s, WorkflowState st) {
    return st.completedSteps().containsAll(PREREQS.get(s));
}
Now the rule is declarative, testable by iterating the map, and MATCH_SKILLS checks all of its real prerequisites rather than only the previous step.
6.3 completedSteps is a HashSet. Is that a problem? Not for gating (membership only), but it loses order, which matters for audit trails and handoff summaries ("what was done, in what order"). Use EnumSet (compact, ordered by enum declaration) or LinkedHashSet (insertion order) — or keep a separate List of completion events with timestamps. For concurrent workflows, use a thread-safe structure.
6.4 Status becomes COMPLETED after each step. What's wrong? WorkflowStatus should describe the workflow, not the last step: IN_PROGRESS while steps remain, COMPLETED only when all required steps are done (or GENERATE_RECOMMENDATION finishes), BLOCKED on a failed gate. A consumer reading COMPLETED after step 1 would wrongly think the job is finished. Derive status from state instead of setting it ad hoc: completed.containsAll(ALL_STEPS) ? COMPLETED : IN_PROGRESS.
6.5 Should a blocked step throw IllegalStateException? Debatable. An exception is fine for programmer errors (calling steps out of order in code). But when the model proposes an out-of-order tool call, that is an expected event: return a structured "blocked: complete ANALYZE_RESUME first" tool result so the model can adapt, instead of crashing the loop. A custom checked/unchecked PrerequisiteNotMetException carrying the missing step is clearer than a generic IllegalStateException.
6.6 Design a self-contained escalation handoff. What fields and why?
FieldWhy
workflowIdCorrelate with logs and tickets
originalGoal / customer issueReceiver has no conversation
conversationSummary (actions taken)Avoid repeating work
rootCauseAnalysis (facts found)Fast diagnosis
recommendedActionClear next step
Possible additions: last completed step, timestamps, error details, confidence. Trigger it from code on defined conditions (policy gap, repeated failure, explicit user request for a human, no progress), not on sentiment guesses.
6.7 Hooks vs prompt vs gate: what is the Agent SDK "hook" equivalent of WorkflowValidator? A PreToolUse-style hook intercepts a tool call before execution and can allow, deny (with a message returned to the model) or modify it. WorkflowValidator.canExecute is the same idea hand-written: deterministic code between "model asked" and "tool ran". A PostToolUse hook is the counterpart for normalising or filtering tool output (e.g. trimming fields) before the model sees it.

Topic 7Java design questions

7.1 Why use record for ToolCall, ToolResult, ResearchFinding, etc.? Records are concise immutable data carriers: final fields, canonical constructor, equals/hashCode/toString for free. Immutability makes them safe to share across threads and ideal for messages passed between agents. Limits: shallowly immutable (a List field can still be mutated unless you wrap it with List.copyOf in a compact constructor) and they cannot extend classes.
7.2 Would you model StopReason as an enum or something else? How would you use the compiler to protect against new values? An enum is right for a closed set. Use an exhaustive switch expression (no default) so adding a new constant produces a compile error wherever it is unhandled: 
String action = switch (reason) {
    case TOOL_USE -> "run tool";
    case END_TURN -> "finish";
};
For the real API, map unknown strings explicitly (an UNKNOWN value or an exception) instead of silently treating them as END_TURN.
7.3 Which SOLID principles do the classes demonstrate? Give one concrete example each.
  • S — Planner plans, Executor executes, Evaluator evaluates.
  • O — new tool = new class + register; loop unchanged.
  • L — MockClaudeClient and a real client are interchangeable behind LLMClient.
  • I — small interfaces (BaseTool has two methods).
  • D — AgentLoopV2 depends on LLMClient, not the mock.
7.4 How would you add dependency injection / avoid hard-coded new calls in the loop? Pass collaborators through the constructor (new AgentLoopV2(client, registry, maxIterations)). That is plain constructor injection — no framework required. A framework (Spring) only helps when wiring becomes large. Also make MAX_ITERATIONS a constructor/config value so tests can use 2 and production 20 without editing code.
7.5 Is AgentState thread-safe? Does it need to be? No (plain mutable fields). A single-threaded loop does not need it. It becomes a concern if you parallelise subagents sharing state, or run several agents concurrently on one instance. Prefer one AgentState per run (no sharing) and immutable messages; if sharing is unavoidable, use confinement or concurrent collections / locks.
7.6 Logging: System.out.println vs a real logger? Use SLF4J/Logback (or java.util.logging) with levels and structured fields (runId, iteration, toolName, durationMs, stopReason). For agents, a per-iteration trace (request summary, stop_reason, tool, latency, token usage) is the primary debugging tool. Never log secrets or full user PII.

Topic 8Testing

8.1 How do you test an agent whose real model is non-deterministic? Layered approach: (1) unit tests with the scripted mock for loop logic, tool flow, gates, parsing; (2) contract tests that the real-client adapter maps SDK JSON to ClaudeResponse correctly (use recorded fixtures); (3) a small set of live evals scored on properties (correct tool chosen, no forbidden call, answer contains required facts) rather than exact text, run on a schedule.
8.2 Write the test for the engine's untested blocked path. 
@Test
void blockedStepSetsBlockedAndThrows() {
    var engine = new WorkflowEngine(new WorkflowValidator());
    var state  = new WorkflowState();

    assertThrows(IllegalStateException.class,
        () -> engine.execute(WorkflowStep.MATCH_SKILLS, state));

    assertEquals(WorkflowStatus.BLOCKED, state.getStatus());
    assertFalse(state.getCompletedSteps().contains(WorkflowStep.MATCH_SKILLS));   // no side effect
}
Also test the happy path order and that a blocked attempt does not corrupt previously completed steps.
8.3 What tests would catch the "always 100% coverage" bug? A negative test: make one subagent return nothing (or a fake coordinator that skips "Market Trends") and assert completeness < 1.0 and that gaps contains that topic. If a metric has no test where it fails, it can silently become meaningless.
8.4 What does SubagentIsolationTest really prove, and what can't it prove? It proves the Java subagent's output depends only on the passed ResearchContext (change the context, output changes; nothing read from globals). With hard-coded subagents it is largely structural. It cannot prove isolation of a real LLM subagent — that is guaranteed by what you put in its prompt and tool set, which you verify by inspecting the prompt your code builds.
8.5 Why assert the number of mock calls in loop tests? To catch loops that ask the model too many or too few times (e.g. an off-by-one in the cap, or a path that skips END_TURN). iterationCount, history size and mock-call count together pin the behaviour precisely.

Topic 9Scenario & debugging questions

9.1 The agent keeps calling job_search with the same arguments until MAX_ITERATIONS. What do you check?
  1. Is the tool_result actually appended to history (with the correct tool_use_id)? If not the model never sees an answer.
  2. Is the result empty/ambiguous or an unexplained error? The model may retry hoping for a different answer.
  3. Is the tool description unclear about what a successful result means?
  4. Is history being truncated or replaced by a summary that loses the earlier result?
  5. Add loop detection: same tool + same args N times -> stop and escalate.
9.2 The agent finishes early, before running the second tool. Likely causes? Terminating on text content (content[0].type=="text" or phrase matching) instead of stop_reason; treating max_tokens as done; or the loop breaking after the first tool because of a misplaced break/return. Check logged stop_reason for each iteration.
9.3 Your report says "all topics covered" but the Salary section is junk. Why, and what do you change? The default branch routed Salary Analysis to SkillsMatchAgent, which returned a hard-coded finding; the coverage metric counted it. Fixes: dedicated agent or explicit "unsupported" failure, a coverage check based on evidence (source present) and topic relevance, and a negative test.
9.4 Costs exploded after adding more tools. Why, and what do you do? Every call re-sends tools[] and the whole history; more tools means more input tokens per iteration, and more tools can also cause extra wrong-tool calls. Mitigate: fewer, sharper tools; split by subagent; prompt caching for the static prefix; trim large tool outputs; cap iterations; set a per-run token/cost budget.
9.5 A user asks for step 3 before step 2 is done. What happens in each design (prompt-only vs gate)? Prompt-only: the model may comply and skip a prerequisite — probabilistic. Gate: canExecute returns false, the step is BLOCKED, and the model (or caller) gets a message naming the missing prerequisite so it can run it first. The gate gives a guarantee; the prompt gives a hint.
9.6 Explain the whole architecture in 60 seconds. "An agent is a goal-driven loop. State holds the memory, a decision-maker picks the next action, an executor runs registered tools, and a stop condition ends the run. In Catalyst the decision-maker evolved from a rule-based Planner to a Claude-style client driven by stop_reason — TOOL_USE runs a tool and loops, END_TURN finishes, with an iteration cap only as a safety net. On top I built hub-and-spoke orchestration: a coordinator decomposes the goal, passes explicit context to specialist subagents, and aggregates findings that carry provenance. Finally, ordering rules live in code — a prerequisite gate plus structured handoff — because prompts aren't enforcement. Everything sits behind small interfaces, so swapping the mock for the real SDK is a one-class change, and the mock keeps tests deterministic."

Q1. An agent's decision-making can be rule-based or model-driven (LLM). Is that the right way to think about it?

Yes, with the precise vocabulary Anthropic uses. In Building Effective Agents the distinction is:

WorkflowAgent
Who controls the pathYour code (predefined paths; the LLM is called at fixed points)The LLM dynamically directs its own process and tool use
PredictabilityHigh, repeatable, easy to testLower; flexible, handles open-ended tasks
Cost / latencyLowerHigher (more model calls)
Best forWell-defined tasks with known stepsProblems where steps cannot be predicted in advance
  • So "rule-based" = code decides the next step; "model-driven" = the LLM decides it, using stop_reason and tool results to loop.
  • Model-driven tool selection is the default in agentic loops. Programmatic control is added where compliance demands it (financial, security, regulatory).
  • Guidance: use the simplest thing that works (single call → workflow → agent). Don't build an agent when a workflow will do.
  • Real systems are hybrid: the LLM decides within guardrails that code enforces.
Catalyst-specific Phase 1's Planner is the rule-based decision-maker (really workflow-style); Phase 2's LLMClient is the model-driven one. The rest of the skeleton (state, loop, registry, tools) is unchanged between them.
Q2. When should I use the LLM, and when rules? What is the difference between rule-based (programmatic) and prompt-based?

Rule-based and programmatic are the same thing: deterministic code. Prompt-based is different: it is an instruction to the LLM, so it is still model behaviour — probabilistic. This is one of the most tested distinctions in the exam (programmatic enforcement vs prompt-based guidance).

Programmatic (hooks, gates, validators)Prompt-based (system prompt, instructions, few-shot)
Executed byYour application codeThe model
GuaranteeDeterministic — cannot be skippedProbabilistic — usually followed, can be missed or overridden (e.g. by injected text)
Right forRules where a single failure is unacceptableJudgement, tone, format, preferences, guidance

Prompt-based is how you steer the model; programmatic is how you constrain it. They complement each other.

Use programmatic enforcement for

  • Security and identity: authentication/OAuth, authorisation, permission checks.
  • Prerequisite ordering: e.g. block process_refund until get_customer has returned a verified customer.
  • Business and compliance limits: e.g. refunds over a threshold are blocked and redirected to a human.
  • Data normalisation: e.g. a PostToolUse hook converting inconsistent date/status formats before the model sees them.
  • Hard limits: iteration cap, budgets, allowed-tools list.

Use the LLM (steered by prompts) for

  • Unstructured input, ambiguous intent, free-text understanding.
  • Choosing among tools when the right one depends on context.
  • Summarising, extracting, classifying, drafting, explaining.

Related controls worth knowing

  • tool_choice (auto / any / specific tool / none) can force a tool within one request: a soft control, not a cross-turn workflow guarantee.
  • Few-shot examples and clearer instructions improve compliance but never make it guaranteed.

OAuth / credentials, concretely

  • The auth flow is 100% code. The LLM never decides who is allowed in.
  • Keep tokens and secrets out of the prompt; the tool or client layer attaches credentials (for MCP, via configuration/environment variables, not model text).
  • Authorise from the authenticated session identity, never from what the user or model claims.
Decision test: "If the model gets this wrong once in 1,000 runs, is that acceptable?" No → programmatic. Yes and it needs language understanding → LLM with a good prompt. Both → the LLM proposes, code disposes.
Catalyst-specific WorkflowValidator.canExecute, the registered-tools-only lookup and MAX_ITERATIONS are the programmatic controls; the system prompt line "analyse the resume before matching skills" would be the prompt-based one.
Q3. A coordinator passes sub-tasks to subagents via context. How are subagent failures handled, and what governs the coordinator itself?

Part A — Subagents and context (real mechanics)

  • In the Claude Agent SDK / Claude Code, a coordinator spawns subagents through the Task tool (named Agent in newer versions). The coordinator's allowed tools must include it.
  • Each subagent has isolated context: it does not inherit the coordinator's conversation. It sees only its own prompt, so the goal, assigned sub-task, expected output format and any prior findings must be passed explicitly in that prompt.
  • Subagents are defined with a description, system prompt and a restricted tool set (least privilege).
  • Hub-and-spoke: all communication goes through the coordinator; subagents don't talk to each other.
  • Parallelism: independent sub-tasks can run in parallel by emitting several Task calls in one response.

Part B — Handling subagent failure (error propagation)

  1. Recover locally first. The subagent retries transient errors (timeouts, rate limits) itself. Only unresolved failures go up to the coordinator.
  2. Return structured error context, not a bare failure: failure type, what was attempted (query/inputs), any partial results, and possible alternatives. This lets the coordinator choose intelligently.
  3. Distinguish "failed" from "empty". An access/timeout failure is different from a valid search that returned no results. Never report a failure as an empty success.
  4. Coordinator decides (retry with adjusted instructions or more context, use an alternative source, or proceed with partial results).
  5. Proceed with partial results and annotate coverage gaps in the final output, instead of hiding them.
Anti-patternWhy it's wrong
Silently suppressing the error / returning empty as successThe coordinator can't recover and the final answer looks complete when it isn't
Terminating the whole workflow on one subagent failureThrows away good work from the other subagents
Generic status like "operation failed"No information to decide on recovery
Unbounded "try again" loopsJust another runaway loop; cap retries

Q4. Does workflow enforcement live inside the agent or outside of it?

Outside the model's control, inside your application. The LLM proposes; the code that hosts the agent (the harness) decides whether the action runs. The model cannot be the referee for its own behaviour, because it may err or be manipulated by prompt injection.

Real mechanism: Agent SDK / Claude Code hooks

  • Hooks are code run by the host application at defined points in the agent lifecycle, e.g. before a tool runs (PreToolUse) and after (PostToolUse).
  • A pre-tool hook can allow, deny (with a reason returned to the model) or modify the call. A post-tool hook can normalise or trim output before the model sees it.
  • They are not part of the model or the prompt, so the model cannot talk its way past them.

"Inside" vs "outside" depends on what you call the agent

"Agent" means…Where enforcement sits
Just the LLMOutside it: code wrapping the model.
The whole program (LLM + loop + tools)Inside the program, but in a part the model can't skip or edit — e.g. in the tool-execution step, before the tool runs.

What matters is not the class or package; it is that the model has no path around the gate.

With multiple agents

  • Workflow rules (order, prerequisites, limits): one engine above the coordinator, not copied into every subagent.
  • Tool rules: give each subagent only the tools it needs (least privilege), and validate arguments in the tool implementation.
  • Data and permission rules: in the backend, so they hold even if the agent layer is compromised (defence in depth).
One-liner: "The agent proposes; the host application disposes. Enforce in deterministic code that wraps the agent, and repeat the most critical rules one layer further out in the backend."

Two gaps: the coordinator and subagents themselves do not consult the validator (acceptable, since the gate is one level above them), and the engine creates its own new WorkflowValidator() and is created with new inside the workflow, so neither can be swapped or mocked in tests.

Q6. What is the difference between code and an LLM? In the end the LLM is the brain that decides and reasons, even by writing code — right?

Half right. The LLM is the brain for deciding what to try. But it has no hands: it never executes anything. It only produces text (tokens). Something else — your code — reads that text and decides whether and how to act on it. The real difference is not "who thinks" but who executes, who decides the rules, and when the rules were fixed.

A useful analogy

The LLM is a skilled employee who can draft anything. Code is the company's systems and policies: the bank's approval workflow, access badges, audit log. The employee decides what to request; the systems decide what actually goes through. You wouldn't let the employee rewrite the approval system while using it.

One-liner: "The LLM is the brain for choosing and proposing; code is the hands and the veto. The LLM never executes anything, and the rules it must obey are written by humans before runtime, which is why enforcement belongs in code."

These are informal industry terms, not official Anthropic or exam vocabulary, so what matters is the idea behind them. The difference is who controls the flow.

They are not exclusive. A single system often mixes them. For example, a code-driven workflow engine (no LLM control) calls an LLM-driven subagent for the research step, and inside that subagent one tool is itself an LLM-backed summariser. Each component can be placed on this spectrum:

Plain code → LLM-backed (LLM as a function) → LLM-driven (LLM runs the loop)

If "LLM backend" means something else

Some people say "LLM backend" for the model provider or inference service behind the app: the Anthropic API, Amazon Bedrock, Google Vertex AI, or a self-hosted model. That is a deployment question (which model, which endpoint, what limits and cost), separate from who controls the flow. In a well-designed system the backend sits behind one interface so you can swap it without touching the loop.

Quick test: remove the LLM and ask "does the program's path still exist?" If the path is fixed by code and the LLM only fills in text at certain steps, it is LLM-backed. If the LLM chooses which step or tool comes next, it is LLM-driven.
Catalyst-specific
  • AgentLoopV2 has the LLM-driven shape: the loop does whatever the LLMClient returns (TOOL_USE continues, END_TURN stops). Today the client is the scripted MockClaudeClient, so the shape is real but the "brain" is a script.
  • CoordinatorAgent and the three subagents are plain code today, so they are neither. If a subagent's research(context) simply called an LLMClient once and returned its text, it would be LLM-backed. If it ran its own tool loop, it would be LLM-driven.

Q8. Follow-up: is an LLM-backed app basically rule-based code that calls the LLM to get a tool_result? And do AI apps usually start LLM-backed and become LLM-driven when the application needs it?

Part 1 — Mostly right, with one correction

  • Right: in an LLM-backed app the control flow is rule-based. Your code follows fixed rules and calls the LLM at chosen points, then uses the answer.
  • Correction: the LLM does not return a tool_result. The direction is the opposite.
    • The LLM returns a response: text, structured output, or a tool_use request.
    • A tool_result is what your code sends to the LLM after it ran a tool the model asked for.
    So in a plain LLM-backed step you usually just get text or structured data back and your code continues. The tool_use / tool_result exchange mostly belongs to the LLM-driven loop.

Part 2 — Yes, that is the recommended path, but it is not a mandatory ladder

Anthropic's guidance in Building Effective Agents is to use the simplest solution that works and add complexity only when it clearly pays off. Agentic systems trade higher cost, latency and variance for flexibility.

STAGE 1
Single LLM call
Good prompt, maybe retrieval and examples. Often enough.
STAGE 2
LLM-backed workflow
Fixed steps in code: chain, route, run in parallel. LLM does language work at each step.
▼only if the steps cannot be predicted in advance
STAGE 3

STAGE 4

When it makes sense to move up a stage

  • You cannot list the steps in advance (the number and order of steps depend on what is found).
  • Fixed branching keeps growing and breaking on new cases.
  • Your evaluations show the simpler version cannot reach the quality you need.
  • The extra cost, latency and variance are acceptable for the value gained.

Reasons to stay put

  • The process is known and repeatable, so predictability and cost matter more than flexibility.
  • Regulated or high-stakes flows where every path must be auditable.
  • Many strong production systems are deliberately workflows. LLM-driven is not a "more advanced and therefore better" level.
Moving up never removes the code layer. Even a fully LLM-driven agent keeps its gates, hooks, limits and backend permissions in code. You are changing who chooses the next step, not who is allowed to act.
Exam angle: when a question asks for the right architecture, prefer the simplest approach that meets the requirement, use programmatic enforcement for must-never-fail rules, and reach for a model-driven agent only when the task is genuinely open-ended.
Catalyst-specific Catalyst's progression is a learning path, not the production recommendation above. Phase 1 used a rule-based Planner. Rules of thumb

  • Default to closed-ended thinking. If you can turn the task into fixed steps, do. It is cheaper, faster and easier to test.
  • Open-ended does not mean unconstrained. Still enforce order, limits and permissions in code (the VETO from the core principle).
  • A result you can verify makes agents safer. Tests, schema checks or lookups give the loop real feedback instead of relying on the model's own opinion.
  • Mixed tasks are common. Keep the closed parts in a workflow and give only the open step to an agent.

Exam angle: a requirement like "must follow these exact steps" or "must be auditable" points to a workflow with programmatic enforcement. A requirement like "the steps depend on what the research finds" points to a model-driven agent or orchestrator. Pick the simplest option that meets the requirement.

Q10. In the gate, do we also need a human?

Yes, in some gates. A gate is programmatic, but it does not have to decide alone. It has three possible outcomes: allow, deny, or ask a human. The human is one way the gate gets its verdict, and the gate still enforces that verdict.

When a gate should involve a human

  • Irreversible or high-value actions: payments above a threshold, deleting data, sending external messages.
  • Policy exceptions or gaps: the rules do not cover the case, or the request is ambiguous.
  • Sensitive data access or export.
  • The user explicitly asks for a person, or the agent cannot make progress.

When it should not

Prerequisite order (step B only after step A)NoFully decidable by logic, a human adds delay and nothing else

Design rules for the human step

  • Code decides when to ask, not the LLM. Triggers are programmatic (threshold, tool category, data class). The LLM can raise a flag, but it should not be the only trigger.
  • Fail closed. If no human answers within the time limit, the gate denies.
  • Show the human what they need: the proposed action, its arguments, the reason the gate asked. A vague prompt gets rubber-stamped.
  • Keep it rare. Too many approvals cause fatigue and blind approval, which defeats the gate.
  • Log every decision for the audit trail.

Real mechanism

In the Claude Agent SDK and Claude Code, a PreToolUse hook can return a permission decision of allow, deny or ask. Ask pauses the action and prompts the user for approval, so the human gate is built into the hook. The human also appears at design time, since a person writes the gate rules in the first place.

One-liner: "A gate has three outcomes: allow, deny or ask a human. Code decides when a human is needed, the human supplies the judgement, and the gate enforces the answer. No answer means deny."
Catalyst-specific WorkflowValidator.canExecute() returns a plain boolean, so the gate has only allow and deny. WorkflowEngine turns a deny into BLOCKED and an exception. There is no "ask a human" outcome, and WorkflowHandoff is an after-the-fact record, not a mid-run approval. A natural extension is to return a decision with three values (ALLOW, DENY, NEEDS_APPROVAL) and make the engine pause the step on the third.
