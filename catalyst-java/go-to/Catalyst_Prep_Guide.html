Start hereThe big picture

An agent is a program that takes a goal, repeatedly decides what to do next, acts using tools, looks at the result, and stops when the goal is met. A plain chatbot answers once; an agent loops.

Goal→ Plan→ Execute tool→ Evaluate→ Done?→ no: back to Plan / yes: Final answer

Key idea: the architecture is built so that only the "decision maker" changes between phases. Everything else (state, loop, registry, tools) stays the same. That is good design — and a great interview talking point.

Phase 1The six core classes

Think of a small company: the Agent is the front desk, the AgentLoop is the manager who keeps work moving, and the others are specialists.

Agent

Entry point. You call agent.run(goal). It creates the state and hands over to the AgentLoop.

AgentState

The agent's memory: goal, result, history, iterationCount, completed flag. Everything the loop needs to know is here.

Planner

Decides what next. E.g. "search java jobs" → job_search; "analyze my resume" → resume_analyzer.

Executor

Actually runs the chosen tool: tool.execute(input). Does no thinking, just doing.

Evaluator

Decides whether to continue. Today: result != null. Later: look at TOOL_USE vs END_TURN.

AgentLoop

The heart. Repeats Plan → Execute → Evaluate until done (or a safety limit hits).

Separation of concerns

Each class has one job. Because the Planner only plans and the Executor only executes, you can replace the Planner with Claude later without touching the Executor. This is the Single Responsibility Principle in action.

Safety boundaries

Phase 1 lists "safety boundaries" as a learning outcome: the agent can only call tools that are registered, and the loop has a bounded number of iterations. An agent should never be able to do arbitrary things — only what you explicitly gave it.

Phase 1Tool infrastructure

ClassRole
BaseTool (interface)Contract every tool follows: definition() and execute(input).
ToolDefinitionThe tool's "business card": name, description, inputSchema. This is what Claude reads to decide whether to use the tool.
ToolRegistryA lookup of tools: register(tool), get(name). Equivalent to the tools[] array you send to Claude.
JobSearchToolConcrete tool #1 – finds jobs.
ResumeAnalyzerToolConcrete tool #2 – analyzes a resume.
// Shape of the contract
interface BaseTool {
    ToolDefinition definition();      // name + description + inputSchema
    Object execute(Object input);     // do the work
}
Why a description matters: with a real LLM, the description and inputSchema are the only way the model knows what a tool does. Vague descriptions = wrong tool choices.
Why a registry? It decouples "which tools exist" from "who uses them". Adding a third tool = register it; no loop changes needed (Open/Closed Principle).

Phase 2Claude-style tool loop

With a real Claude, you don't hand-write a Planner. You send Claude the conversation plus the tools list, and Claude replies with a stop reason telling you what to do next. Phase 2 models that locally.

New building blocks

Why a mock?

Learning, testing and debugging without API keys, credits or internet. Tests become deterministic: the mock always returns the same scripted answers.

The two stop reasons

TOOL_USE

"I'm not finished. Run this tool, give me the result, and I'll continue." → execute the tool, store the result, loop again.

END_TURN

"I'm done; here is my final answer." → mark completed, exit the loop.

The loop (Java)

while (!state.isCompleted()) {                 // also bounded by MAX_ITERATIONS

    ClaudeResponse response = client.nextResponse();

    if (response.stopReason() == StopReason.TOOL_USE) {
        executeTool();                         // run tool, save ToolResult in state
        continue;                              // ask Claude again
    }

    if (response.stopReason() == StopReason.END_TURN) {
        state.setCompleted(true);
        break;
    }
}

Same loop in the Claude SDK (JavaScript)

while (true) {
    const response = await client.messages.create(...);

    if (response.stop_reason === "tool_use") { executeTool(); continue; }
    if (response.stop_reason === "end_turn")  { break; }
}

How it is actually coded

  • ToolCall = (id, toolName, input); ToolResult = (toolCallId, content). The id links a result to its request, like tool_use_id in the API.
  • AgentState gained stopReason and finalResponse (besides goal, result, history, iterationCount, completed).
  • AgentLoopV2 takes an LLMClient. MockClaudeClient (the implementation used today) is a step counter: step 1 → TOOL_USE job_search, step 2 → TOOL_USE resume_analyzer, step 3 → END_TURN (any later call also returns END_TURN).
  • The cap is checked at the top of each iteration: if iterationCount >= MAX_ITERATIONS it prints a warning and breaks.
  • AgentLoopV2 and Phase2Runner hold the same loop. The runner also wraps output in a ToolResult and stops if the tool name is not in the registry.

The safety cap

private static final int MAX_ITERATIONS = 20;
Know this distinction: the primary way the loop stops is END_TURN. MAX_ITERATIONS is only a guard rail against runaway loops (e.g. a model that keeps calling tools forever, costing money). Don't use the cap as the normal stopping logic.

Phase 2.5Sequential tool calls

Real tasks need several steps. Goal: "Find Java jobs and analyse my skills." Claude calls one tool, sees the result, then decides the next step.

Iter 1: TOOL_USE job_search→ Iter 2: TOOL_USE resume_analyzer→ Iter 3: END_TURN

Expected final state

FieldValueWhy
iterationCount3Claude was asked 3 times
history size2Only 2 tool executions are recorded (the END_TURN is not a tool)
completedtrueEND_TURN received
stopReasonEND_TURNLast response
finalResponseavailableClaude's closing answer
Why sequential matters: the second step can depend on the first step's output. That is the foundation of multi-step reasoning — the conversation state (AgentState ≈ messages[]) carries everything forward each iteration.
Common trap: iterations = tool calls + 1. If someone expects iterationCount = 2, they forgot the final END_TURN call.

Phase 3Multi-agent orchestration (hub-and-spoke)

Instead of one agent doing everything, a coordinator splits the goal into sub-topics, hands each to a specialist subagent, collects the findings, checks coverage and produces one report.

Goal→ decompose()→ delegate()→ subagents→ evaluateCoverage()→ aggregate() → ResearchReport
Key rule: subagents never talk to each other. Everything goes through the CoordinatorAgent (the hub). This keeps control, error handling and context in one place.

The cast

ClassJob
CoordinatorAgentDecompose, delegate, aggregate, evaluate coverage. Entry: research(topic).
JobSearchAgentSpecialist for jobs, companies, locations.
ResumeAnalysisAgentSpecialist for resume strengths, weaknesses, skill gaps.
SkillsMatchAgentSpecialist for skill matching and recommendations.
SubTopic (record)One slice of the goal: name.
ResearchFinding (record)One result: claim, analysis, metadata (provenance). Changed in Phase 4.
ResearchReport (record)Final aggregate: topic + list of findings.
CoverageReport (record)covered, gaps, completeness (0.0–1.0).

The four steps

  1. Decompose – goal becomes sub-topics: Job Search, Resume Analysis, Skills Match, Salary Analysis, Market Trends.
  2. Delegate – for each sub-topic the coordinator builds a ResearchContext and calls agent.research(context).
  3. Evaluate coverage – the intended idea: covered = sub-topics that have a finding; gaps = planned sub-topics with none; completeness = covered / planned. (See the honest notes below for what the code does today.)
  4. Aggregate – findings are wrapped in a ResearchReport.

Current implementation – honest notes

  • decompose() is hard-coded to five sub-topics; no model is involved yet.
  • delegate() uses a switch on the name: "Job Search" → JobSearchAgent, "Resume Analysis" → ResumeAnalysisAgent, default (Skills Match, Salary Analysis, Market Trends) → SkillsMatchAgent.
  • Subagents return hard-coded findings (e.g. claim "Java jobs found in Munich"), not real research. Delegation is a sequential loop, not parallel.
  • Coverage logic drifted: after the Phase 4 change evaluateCoverage() lists metadata.retrievedBy (agent names) as "covered", always returns an empty gaps list, and computes completeness as findings.size() / topics.size(). That is always 100% as long as every sub-topic returns something, so it can never report a gap. Good interview example of a metric that cannot fail.
  • The "Refine" step (re-delegate for gaps) is in the docs but not coded.
  • Application.java now switches all five phases (ACTIVE_PHASE is currently PHASE_5), so the Phase 3 and 4 runners are wired in; change the constant to run them.
Interview angle: hub-and-spoke gives observability and consistent error handling, but the coordinator can decompose too narrowly. If the decomposition misses a topic, no subagent will cover it — so coverage evaluation compares findings with the plan and should question whether the plan itself was complete.

Phase 4Context passing & provenance

A subagent starts with isolated context: it knows only what the coordinator puts in its prompt. Phase 3 assumed it had what it needed; Phase 4 makes the handoff explicit. This maps to exam task 1.3 Subagent Invocation & Context Passing and, for metadata, 5.6 Information Provenance.

Coordinator→ ContextBuilder.build(goal, subTopic, priorFindings) → ResearchContext→ agent.research(context) → ResearchFinding (claim + analysis + metadata)
Class / recordFieldsPurpose
ResearchContextoriginalGoal, assignedSubTopic, expectedOutput, priorFindingsEverything a subagent is allowed to know, passed explicitly
ContextBuilderbuild(goal, subTopic, priorFindings)Creates the context; sets expectedOutput to "Provide structured findings"
ResearchMetadatasourceUrl, documentName, pageNumber, confidence, retrievedByProvenance: where a claim came from and how sure we are
ResearchFindingclaim, analysis, metadataA claim always travels with its source info
ResearchOutputfindings, query, timestampStructured return wrapper (defined, not used yet)

What changed from Phase 3

  • Subagents: research(subTopic, goal) → research(ResearchContext). They can only use what is in the context object.
  • The coordinator feeds findings forward: after each subagent it appends "- " + finding.claim() to priorFindings, and the next subagent receives it. Context flows only through the coordinator — still hub-and-spoke.
  • Metadata differs per agent: JobSearch has a source URL; ResumeAnalysis has document "Resume.pdf", page 3, confidence MEDIUM; SkillsMatch has no URL. null fields are allowed when a source does not exist (not fabricated).

Exam angle: the subagent prompt must contain the goal, its assigned sub-topic, the expected output format and any prior findings it needs. Do not rely on the subagent "knowing" the coordinator's conversation. Keep claims and their sources together so conflicts can be annotated instead of silently merged.






  
Phase 5Workflow enforcement & handoff

  
Some steps must happen in a fixed order. Prompts are not enforcement; code is. Telling the model "analyse the resume before matching skills" is a request it may ignore. A prerequisite gate in code cannot be ignored. Maps to exam task 1.4 Enforcement & Handoff Patterns (deterministic gates) and escalation handoffs.


  
Workflow governs the agents: WorkflowEngine decides when the CoordinatorAgent (and so the subagents) may run. Order is enforced by code; the agents do the work.

Structured handoff

  
When a human (or another agent) takes over, they do not see the conversation. The handoff must be self-contained: the original goal, a summary of what was done, the root cause found, and the recommended next action. This matches the exam's escalation guidance (issue, actions taken, facts, recommended step).


  
Current implementation – honest notes

  
    
    
  • The engine itself still only validates and marks the step complete. The real work is the coordinator call added in JobApplicationWorkflow (Phase 3/4 code, hard-coded findings).
    • 
    
  • The step is marked complete before the coordinator runs. engine.execute() calls state.complete(step) first, then JobApplicationWorkflow calls the coordinator. If the coordinator throws, the step already counts as completed. It should be marked complete only after a valid result comes back.
    • 
    
  • Every step calls the same full research (coordinator.research(goal) decomposes into all five sub-topics each time), only the goal text differs. The step is not mapped to a specific subagent, and the report is only printed (findings count), not stored or used by the next step.
    • 
    
  • The gate is strictly linear and only checks the immediately previous step. It works because every step is only reachable through the chain.
    • 
    
  • A blocked step sets BLOCKED and throws. Status is set to COMPLETED after each step, not once at the end of the workflow.
    • 
    
  • The handoff is now created after the last step and stored with state.setHandoff(), but its text is hard-coded (e.g. "Candidate lacks advanced Spring Boot experience"), not derived from the findings.
    • 
    
  • WorkflowExecutionResult is unused. WorkflowState.completedSteps is a HashSet, so it does not keep order.
    • 
    
  • Tests: the validator gate (2 cases), the handoff builder, and one integration test of the full workflow. The engine's throw-on-block path is still untested, and the handoff content is not asserted.
    • 
  


  
Exam angle: use programmatic enforcement (hooks, prerequisite gates) when order or policy must be guaranteed; prompt instructions only give probabilistic compliance. Typical example: block a refund tool until the customer is verified.

Three anti-patterns (common wrong answers)

  

    
Anti-patternWhy it's wrong

    
Parsing text such as "I'm done" / "I have completed"Natural language is unreliable; wording varies.

    
Using an iteration cap as the primary stopCaps only guard against runaway loops; they don't fix early exits. This is why Catalyst's MAX_ITERATIONS is "safety only".

    
Checking content[0].type == "text" for completionA response can contain text and a tool_use block, so the agent exits too early.

PrepareInterview-style Q&A

  
Click a question to reveal the answer. Try answering out loud first.


  
What is an agent, and how is it different from a single LLM call?
    An agent runs a loop: decide → act (tool) → observe → repeat until the goal is done. A single call produces one response and cannot take actions or react to results.

  
Explain the Plan → Execute → Evaluate cycle.
    Planner picks the next action, Executor runs the selected tool, Evaluator checks the result and decides to continue or stop. AgentLoop repeats this and AgentState records progress.

  
What does AgentState hold and why is it important?
    Goal, result, history, iteration count and completed flag. It is the agent's memory; in a Claude integration it corresponds to messages[], which is sent on every call so the model has full context.

  
Why have both BaseTool and ToolDefinition?
    BaseTool is the behaviour (execute). ToolDefinition is the metadata (name, description, input schema) that tells the model what the tool does and what arguments it needs.

  
What is a ToolRegistry for?
    Central lookup of available tools by name. It maps to tools[] in the API, keeps the loop independent of specific tools, and acts as a safety boundary: only registered tools can run.

  
What are the two stop reasons in this project and what does each trigger?
    TOOL_USE → execute the requested tool, record the result, continue the loop. END_TURN → mark completed and return the final response. (The real API has more, e.g. max_tokens, but these two drive the core loop.)

  
Why does the loop need MAX_ITERATIONS if END_TURN already stops it?
    END_TURN is the normal exit; the cap is a safeguard against bugs or a model that keeps requesting tools forever (cost, latency, infinite loops). It must be generous enough not to cut legitimate work (20 here).

  
Why use a MockClaudeClient?
    Deterministic, free, offline. It lets you test loop logic and tool flow without keys, credits or network, and makes unit tests stable.

  
In the sequential scenario, why is iterationCount 3 but history size 2?
    Three calls to Claude (tool_use, tool_use, end_turn) but only two tool executions are recorded in history. The END_TURN call produces the final answer, not a tool run.

  
What is the hub-and-spoke pattern and why use it?
    One coordinator talks to specialist subagents; subagents never talk to each other. It centralises control, error handling, logging and context, and makes clear who owns the final result.

  
What does the CoordinatorAgent do, step by step?
    Decompose the goal into sub-topics, delegate each to a specialist, evaluate coverage (covered vs gaps vs completeness), then aggregate findings into a ResearchReport.

  
How is completeness calculated and what is its weakness?
    Covered distinct sub-topics divided by planned sub-topics. It only checks that a finding exists, not that it is good, and it cannot detect topics the decomposition never planned.

  
Why must a subagent's context be passed explicitly?
    Subagents have isolated context; they do not inherit the coordinator's conversation. Without an explicit goal, assigned sub-topic, expected output and prior findings (ResearchContext) they work blind or duplicate effort.

  
How could Phase 3 delegation be made faster?
    The sub-topics are independent, so launch the subagents in parallel (several Task calls in one response) instead of looping sequentially.

  
What are the known limitations of the current Phase 3/4 code?
    Hard-coded decomposition, hard-coded subagent output, unknown sub-topics routed to SkillsMatchAgent by the default branch, no refine step, sequential delegation, and a coverage metric that always reports 100% with no gaps.

  
Why enforce workflow order in code instead of the prompt?
    Prompt instructions are followed probabilistically; a gate (WorkflowValidator.canExecute) is deterministic. If the prerequisite is not completed the step is blocked no matter what the model says.

  
What does a good handoff contain and why?
    Original goal, summary of what happened, root cause and recommended action (WorkflowHandoff). The receiver has no access to the conversation, so it must stand alone.

  
What are the gaps in the current Phase 5 code?
    The workflow now calls the coordinator and creates a handoff, but the step is marked complete before the coordinator runs, each step runs the same full research, the report is not passed on, the handoff text is hard-coded, WorkflowExecutionResult is unused, status becomes COMPLETED after every step, and the blocked path (exception) has no test.

  
Why is the current completeness metric weak?
    It divides the number of findings by the number of planned sub-topics, and every sub-topic always produces a finding, so the result is always 1.0 and gaps is always empty. A useful metric must be able to fail: compare required topics against findings that actually contain evidence.

  
What goes into a good subagent context?
    The original goal, the assigned sub-topic, the expected output format and any prior findings it needs (ResearchContext). Passed explicitly because subagents do not inherit the coordinator's conversation.

  
Why does a finding carry metadata?
    Provenance: source URL or document, page, confidence and which agent retrieved it. It lets a synthesis step trace claims, show confidence, and annotate conflicts between sources. Unknown fields stay null instead of being invented.

  
What changes when the real SDK replaces the mock?
    Only the client: write a real LLMClient implementation that wraps the Anthropic SDK's client.messages.create() and pass it instead of MockClaudeClient; AgentLoopV2 needs no change. AgentState, AgentLoopV2, ToolRegistry, ToolCall, ToolResult and StopReason stay unchanged — the benefit of the abstraction.

  
What is the role of tool_result in the conversation?
    After the model requests a tool, you run it and send back a tool_result tied to that request. Claude uses it to decide the next step. Without it Claude cannot continue reasoning.

  
How would you add a third tool?
    Implement BaseTool with a clear ToolDefinition, register it in ToolRegistry, add a test. No change to AgentLoop (Open/Closed principle).

  
What can go wrong in agent loops, and how does this design handle it?
    Infinite loops (MAX_ITERATIONS), unknown tool names (registry lookup fails safely), bad tool output (Evaluator / error ToolResult), lost context (AgentState keeps history).

THE CORE PRINCIPLE

  
The LLM is the brain for choosing and proposing. Code is the hands and the veto.


  

    

      

      STEP 1
      
BRAIN
LLM
      
Chooses and proposes. Understands language, picks a tool, drafts an answer. Its output is only text: a request. Nothing has happened yet.

    

    
➜PROPOSAL

    

      

      STEP 2
      
VETO
YOUR CODE
      
Allows or refuses. Gates, hooks and validators block anything outside the rules, and tell the model why.

    

    
➜IF ALLOWED

    

      

      STEP 3
      
HANDS
YOUR CODE
      
Executes. Runs the tool, calls the API, changes the data, and returns a tool_result to the model.

    

  


  

    
DESIGN TIME (HUMANS)Write, review, test and version the rules

    
RUN TIME (EVERY REQUEST)LLM proposes → code checks → execute or refuse

AGENT  = goal -> loop(plan, execute, evaluate) -> answer
STATE  = goal, result, history, iterationCount, completed   (~ messages[])
TOOLS  = BaseTool + ToolDefinition(name, description, inputSchema) in ToolRegistry (~ tools[])

PHASE 1  Planner decides (rules)         Evaluator: result != null
PHASE 2  Claude decides (stop_reason)    TOOL_USE -> run tool & continue
                                         END_TURN -> done, break
PHASE 2.5 TOOL_USE, TOOL_USE, END_TURN   iterations=3, history=2, completed=true
GUARD    MAX_ITERATIONS = 20  (safety only; END_TURN is the real exit)
MOCK     LLMClient (interface) <- MockClaudeClient = scripted fake of client.messages.create()
PHASE 3  CoordinatorAgent: decompose -> delegate -> evaluateCoverage -> aggregate
         hub-and-spoke: subagents never talk to each other
         completeness = covered / planned sub-topics
PHASE 4  ContextBuilder -> ResearchContext -> agent.research(context) -> ResearchFinding(claim, analysis, metadata)
         priorFindings flow through the coordinator only; metadata = provenance
PHASE 5  WorkflowValidator.canExecute(step,state) gate -> WorkflowEngine.execute -> CoordinatorAgent.research(goal)
         per step; after step 4 HandoffBuilder.build -> WorkflowState.handoff
         blocked => BLOCKED + IllegalStateException; WorkflowHandoff = self-contained summary
         prompts are not enforcement, code is
LATER    swap Mock -> Anthropic SDK; loop, state, registry stay unchanged
EXAM     stop_reason is THE signal. Never: parse "I'm done", cap-as-primary, content[0]==text.
         Keep full history incl. tool results. D1 = 27% of CCAR-F.
